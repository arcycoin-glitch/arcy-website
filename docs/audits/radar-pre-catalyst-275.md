# Radar pre-catalyst shadow audit — issue #275

Date: 2026-11-17 UTC. Scope: `lib/radar-v2/pre-catalyst.js`, a read-only shadow probe, and tests. The public Radar response, Discovery Score/version, cards, Pons Launch, Info button, Search and homepage files are untouched. Shadow is **OFF by default** and is run manually with `RADAR_PRECATALYST_SHADOW=1 node scripts/probe-radar-pre-catalyst.cjs`. It makes at most one request to each of the four **existing** Radar API sections; it does not call OHLCV, add a route, write a database or alter public ranking.

## Source feasibility and credit decision

- CoinGecko [pool OHLCV reference](https://docs.coingecko.com/reference/pool-ohlcv-contract-address) documents exact network/pool daily candles as `[timestamp, open, high, low, close, volume]`, with `meta.base` and `meta.quote`. It does **not** supply historical liquidity in that tuple. The engine requires separate exact-pool, timestamp-bound liquidity witnesses before a candle may support an 8x exclusion or a clean history verdict.
- CoinGecko's [pricing table](https://www.coingecko.com/en/api/pricing) lists 10,000 monthly Demo credits and 100 calls/minute. Its [license guidance](https://support.coingecko.com/articles/1043089972-what-are-the-differences-between-commercial-and-custom-licenses) says Demo/keyless lacks commercial rights; attribution alone does not authorize commercial use. ARCY's existing source policy already forbids keyless production polling. **No new OHLCV HTTP read path is enabled.** Availability for Arc and Robinhood pools under the current account was not demonstrated.
- Existing Radar uses CoinGecko/GeckoTerminal candidate windows, DEX Screener exact-contract cross-check when approved, and Pons on-chain factory reads. These establish neither official token-to-project affiliation, historical liquidity, organic unique buyers, nor a dated official catalyst. DEX Screener current pair snapshots are not treated as historical OHLCV.
- Existing `demoBudget(80 minutes)` models 13 CoinGecko calls per shared four-section cycle, about 7,020/month. The live manual probe reported **4 CoinGecko calls per section** (16 reported, cold-cycle upper estimate 8,640/month if repeated 540 times), plus 1 DEX call per section and 68 RPC calls reported across sections. Shared caching can reduce actual calls; cold starts and multiple instances can increase them. The existing 7,500-credit per-process ceiling and shared quota gate must remain. Adding even **one** new OHLCV read for 15 distinct three-chain candidates per cycle would add 8,100 calls/month before Pons and current Radar costs; two pools would add 16,200. This is outside the safe Demo budget. The shadow probe itself adds **zero direct provider/RPC calls in code**, but its four existing API reads may cause normal Radar refreshes when caches are cold.

## Deterministic selection policy

The pure engine first rejects wrong-chain/canonical/impostor contracts. An official exact-token affiliation, active product with two distinct source-backed releases, future dated official event, verified buyer clusters, executable exit, reviewed contract permissions and complete pool history are all required for `ELIGIBLE`. Missing, stale, contradictory or rumor evidence is `REVIEW` and never promoted. Verified sell disabled, unrestricted mint, abandoned project or sustained 8x history is `EXCLUDE`. A sustained 5x–below-8x is `REVIEW`. A price decline by itself gives neither credit nor veto.

History is inspected separately per exact pool for both 30-day and 7-day windows. The algorithm sorts chronological candles, uses three-candle median closes for both baseline and later peak, and demands volume plus separately witnessed historical liquidity on each candle. A one-candle wick, dust low or missing/migrated pool cannot clear the gate. A verified 8x in **either** window remains excluded after a later collapse. The engine never combines different quote currencies or token contracts. Eligible results would retain the existing `arcy-discovery-2` score for ordering and cap at five per current network. No opportunity score or return prediction is published.

Input is capped at 400 candles and two pools per candidate. The sustained-baseline scan is linear after sorting. A local Node 24 CPU microbenchmark of 10,000 `windowRunup` evaluations with 400 candles took 1,309 ms total (about 0.13 ms/evaluation); this measures pure CPU only, not network or future source-verification latency.

The positive fixture uses explicitly synthetic, attested evidence to test algorithmic behavior. A real official-source attestation and historical-liquidity adapter have **not** been approved or connected. A caller-supplied `publisherVerified` flag must not be treated as independent proof in any future public integration.

## Independent 24-hour anti-pump exclusion (handoff hardening)

The selector can now additionally issue an **EXCLUDE** if the existing Radar has a mature exact-pool `CROSS_VERIFIED` 24-hour change and **both** independent provider readings independently confirm at least +700% in that same completed 24-hour window. This is a mathematically bounded **8x over 24 hours**, not lifetime return and not a 7d/30d OHLCV substitute. Single-source observations, token-wide/pool-scope mismatches, pools under 24 hours, missing or stale snapshots, and contradictory readings do **not** trigger this exclusion. No new APIs, provider credits, keys, or persistence are introduced. The gate is still shadow-only and cannot establish that any candidate has *not* previously rallied. The proof is one-way: exclusion only.
